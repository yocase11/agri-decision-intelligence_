# Routing and Transport Audit

## Scope and audit sequence
This report was written before any routing/transport research logic was changed. Protected forecasting, sell/store, warehouse MILP, legacy routing code, datasets, and their outputs were only inspected. The intended new component is a separate research evaluator.

## Data sources and available fields
- `tamilnadu_full_warehouse_dataset (1).csv` supplies warehouse IDs, coordinates, capacities labeled MT, crop-support flags, and storage rates labeled `Storage_Cost_per_MT`. Warehouse coordinates are present in 103 rows, but source provenance is not independently verified.
- `warehouse_optimization_results.csv` supplies the selected warehouse per allocated scenario, allocated quantity in quintals, scenario/model/date/horizon, cost, utilization, and a `distance_km` value generated by the warehouse evaluator from the configured warehouse-coordinate centroid using Haversine.
- `warehouse_summary.csv` supplies one scenario/crop allocation summary.
- `sell_store_decisions.csv` contains scenario quantities but no farmer, collection point, market, or customer coordinates.
- `farmer_crop_dataset (1).csv` contains Farmer_ID, crop, yield per acre, and season, but no latitude/longitude, acreage, vehicle, trip, or route-observation fields.
- No supplied file contains destination demand, delivery windows, vehicle IDs/counts/capacity, road-network observations, actual trip distances, GPS tracks, or route travel-time observations.

## Existing `src/routing.py`
- `get_road_distance_and_time` calls the public OSRM driving route endpoint for a single supplied coordinate pair. A successful response is converted from metres/seconds to km/minutes; errors return `(None, None)`.
- `get_distance_matrix` calls the OSRM table endpoint for a source plus warehouse coordinates and returns distance (km) and duration (minutes); errors return `(None, None)`.
- `best_route` is a single origin-to-one-warehouse route calculation, not a multi-stop VRP. When not offline it tries OSRM, then falls back to Haversine. Its fallback travel time is `max(1, 2 * straight_line_km)` and is not a measured/validated travel time. The returned `used_osrm` flag can be misleading after fallback because it checks whether distance is non-null after fallback.
- `optimize_warehouse` scans candidate warehouses and greedily chooses one feasible destination minimizing its calculated storage plus transport total. It calls the OSRM distance matrix even though it accepts `offline_mode`; otherwise it falls back to haversine. It checks capacity for a single facility and does not split quantities across facilities.
- `compute_transport_cost` converts kg to metric tonnes by dividing by 1,000 and calculates `distance_km * tonnes * cost_per_km_per_tonne`, plus fuel/driver per-km rates and fixed permit/toll amounts. Default base rate is 5.0 per km per tonne; currency/provenance are not encoded in the function. These are configurable inputs, not observed carrier quotes.
- OSRM is a live external HTTP service, not a pinned offline road-network dataset; results can change or fail. The research evaluator will not call it because the available route origin is synthetic, not an actual farmer location.

## Other routing / VRP implementations
- `src/advanced_decision_system.optimize_warehouse_vrp` greedily checks one warehouse at a time and picks the minimum calculated cost.
- Its `vrp_milp` uses binary variables to select exactly one warehouse, with a quantity-capacity check and a distance-times-tonnes cost. This is a single-facility assignment, not a multi-vehicle routing problem; it omits storage cost, crop compatibility, fleet, and route sequencing.
- `src/complete_system.get_distance_matrix` uses OSRM when successful and otherwise computes Haversine distances, then sets fallback duration to `distance * 2` without a validated time unit.
- `src/complete_system.vrp_milp` has binary arc variables, degree constraints and MTZ subtour constraints for a single closed tour over input nodes. It is a TSP-style single-tour problem, not a CVRP: no vehicle fleet, vehicle capacity, demand, multiple vehicles, or time windows are represented. Its nodes are generic inputs, not validated farmer/customer demand points.
- `src/transport_opt.simple_vrp_distance` uses Euclidean distance over latitude/longitude degree values, starting at `(0,0)`; its output is not kilometres and is unsuitable as a transport distance.

## Callers and representations
- `decision_support.run_single_farmer_decision` passes UI/API farmer coordinates and kg quantity to `routing.optimize_warehouse`; warehouse loading is crop-filtered by `mcdm.load_warehouses`.
- `decision_support.run_decision_support` calls `simple_vrp_distance` over up to five warehouse locations, not a farmer-to-warehouse route.
- `src/app.py` and `custom_ui.py` display legacy warehouse/route choices. `custom_ui.py` can fall back to unsupported rows or fabricate a fallback warehouse if loading fails; excluded from research results.
- `src/advanced_decision_system.py` and `src/complete_system.py` contain separate single-warehouse/TSP-style experiments.
- `tests/test_integrated_pipeline.py` calls `best_route` with test coordinates; those are test inputs, not documented farmer-route observations.
- The warehouse research output is the only defensible connection available to this phase: scenario ID -> allocated warehouse ID -> warehouse coordinate -> configured reference origin -> proxy distance and transport cost.

## Routing problem classification
The supplied research data does **not** support farmer-origin routing, multi-warehouse collection, a capacitated VRP, or a CVRP. It contains no actual farmer origins, customer/market destinations, demand nodes, fleet, time windows, vehicle capacities, or route observations. The saved warehouse outputs do contain one allocated warehouse and a simulated quantity per scenario. Therefore this phase will implement a **scenario-based single-leg transport routing evaluation** from the existing synthetic warehouse-centroid reference origin to each MILP-assigned warehouse. It will not be called a VRP and will not report road distance.

## Defensible distance and cost method
- Reuse the existing warehouse reference-origin assumption and destination coordinates from the supplied warehouse file.
- Use Haversine straight-line distance in km only; label source `Haversine` and route type as a reference-origin proxy.
- Recompute route transport as `distance_km * (allocated_quantity_quintal / 10) * transport_rate_inr_per_km_per_metric_tonne`.
- The 5.0 INR/km/MT rate remains a configurable scenario assumption inherited from the warehouse research configuration, not an observed carrier quote.
- Travel time, fleet size, number of vehicles, road feasibility, and time-window feasibility are unavailable and will not be fabricated or reported.
- OSRM comparison is unavailable for research because the only origin is synthetic. No OSRM call is made.

## Falsifiable local hypothesis
For each positive warehouse allocation, recomputing Haversine distance from the same reference-origin coordinates to the assigned warehouse should match the saved `distance_km`; recomputing rate x distance x allocated metric tonnes should match the saved warehouse transport cost. A mismatch would indicate a broken link between warehouse allocation and the new route evaluator.
